## 定位与诚实边界

- 整改链建立在既有“人工复核（`rec_reviews`）”与“治理登记血缘（`rec_governance_links`）”
  之上：只对**已成功且已登记治理血缘**的父作业创建整改。
- 问题来源必须是该作业的一条 `questioned` 或 `rejected` 人工意见，且创建时仍是同一目标
  （任务整体或某候选区域）的**最新**意见。`accepted`、跨作业、不存在或已被后续意见取代一律拒绝。
- 人工意见只是本机署名声明，**不是真值**；整改不证明问题自动解决、不报告精度提升、也不代表
  原 TIFF 通过 P0 质检。
- 原输入 / 模型 / 作业 / 掩膜 / 类计数 / 意见 / 治理快照一律不改；整改只在独立 `rec_corrections`
  表**追加**一条新记录，并另起一个**同模型**的新作业（走原 `JobManager.submit` 与原 worker）。
- 修订版本**不等于**“同一 P0 资产内自动新增版本”：新作业成功后如需治理登记，由既有登记接口
  另建自己的登记单（可有不同 `asset_id`）。本次只记录事实与关联。

## 整改内容

`changes` 与 `replacement` 可各自省略，但必须有至少一个**真实**变化：

- `changes`：仅允许 `source` / `scene_id` / `source_link` / `license_status`，沿用原元数据
  类型与长度约定（`source`、`scene_id` 非空；`source_link`、`license_status` 可为 `null`）。
- `replacement`：**必须且只能**含 `filename` 与 `content_base64` 两个字段；沿用
  `validate_job_payload` 的严格 base64、`.tif`/`.tiff` 扩展名与 40 MiB 上限。
- 只改文件名而字节/规范化元数据未变**不算**整改（返回 400）。

## 接口

| 接口 | 用途 |
|---|---|
| `POST /jobs/<parent>/corrections` | 创建整改。新建 201、幂等复用/恢复 200、未知父作业 404、状态/冲突/容量 409、正文非法 400、提交失败 503 |
| `GET /jobs/<parent>/corrections` | 按父作业列出改正它的整改记录；父作业存在即可读；按 `correction_id` 递增，`limit=50` 有界 |
| `GET /corrections/<id>` | 只读返回整改记录、父/子事实摘要与对照；同一 SQLite 读快照 |

### POST 正文

```json
{"request_id":"稳定UUID","review_id":1,"operator":"流程署名","reason":"整改原因",
 "changes":{"scene_id":"新场景"},
 "replacement":{"filename":"new.tif","content_base64":"..."}}
```

`operator` 必填、trim 后 1..80；`reason` 1..2000；`review_id` 为正 SQLite 整数（不接受 `bool`）；
`request_id` 沿用有界 ASCII 约定（`^[A-Za-z0-9._:-]{1,128}$`）。拒绝未知字段与非法类型。

### GET /corrections/<id> 结构

- `correction`：整改记录（含 `root_job_id`/`parent_job_id`/`review_id`/`revision_no`/
  `child_job_id`/`request_id`/`derived_job_request_id`/`operator`/`reason`/`changes`/
  `is_synthetic_case`/`submission_state`/`prepared_at`/`submitted_at`/`error`）。
- `parent` / `child`：各自事实摘要（`job_id`/`status`/`input_sha256`/`model_sha256`/来源场景许可/
  `attempt_count`、`run_seq`、四类像素（含 255）、`region_count`、治理登记摘要或 `null`、
  最新整体意见（使用原 `reviews` 契约）或 `null`）。
- `comparison`：子作业是否成功、同输入/同模型、修订元数据变化、前后每类像素数及 `delta`
  （有两次成功才比较）、NoData 比率及各自分母（四类像素合计，**不是准确率**）。无成功或无
  校验记录返回 `null` 并说明，不填 0 冒充完成。

- 允许生命周期仅更新 `child_job_id`/`submission_state`/`error`/`submitted_at`；其余不可覆盖。

## 可恢复的两阶段（不修改原 JobManager / jobs.py）

1. **准备事务**（`BEGIN IMMEDIATE`）：校验父作业、意见、容量与真实变化，**持久化 `prepared`
   修订意图**后提交。
2. 调用原 `manager.submit`，创建/复用子作业。
3. 回写 `child_job_id` 与链接状态（独立一次提交）。

**两次提交之间不是原子**，此处如实表达边界：

- 子作业请求号由本记录全局 `request_id` 经 SHA256（固定 namespace）派生，同号重试**始终相同**；
  不使用随机新号重试。
- 若提交成功但回写链接失败，记录保持 `prepared`；同一 `request_id` 重试只会补齐链接，
  原 `manager` 幂等复用同一 job，**不再重新推理**。
- 若 `manager.submit` 本身失败，`submit_correction` 明确抛 503 并保留 `prepared`，附错误说明；
  用户改主意必须换新 `request_id`（新版本须重新通过当前校验）。
- 准备事务回滚不留数据库半记录；已安全发布的文件可保留（不删除、不覆盖）。
- `GET`、启动恢复或普通查询**不自动提交、不自动重跑**；已中断的子作业不重放。

## 网页用法（DEV-20261015-016）

第 8 页“田块识别”的成功结果（五项产物校验通过）里新增**整改复跑与前后对照**面板，
只通过 :class:`RecognitionClient` 调用上面的接口；**页面本身不直接加载模型、不触发推理**，
模型只由已审识别服务在独立子进程显式启动。面板不直接写识别库。

1. 先按[网页识别说明](网页识别.md)启动识别服务与网页；选一个**已成功且已登记治理血缘**、
   并在“人工复核记录”里已保存了最新 `questioned`/`rejected` 意见的作业。
2. 在面板选择作为整改来源的**最新问题意见**（任务整体或某区域），填写操作者署名与原因；
   来源/场景默认复用父作业，只有真正改动的字段才会提交；也可上传替换的 8 波段 TIFF
   （≤40 MiB，模型适用性由原 worker 实际验证）。
3. 点击**“创建整改并复跑”**才提交（`POST /jobs/<父>/corrections`）。预期显示整改编号、
   修订号与新作业编号；“已提交”不等于“已识别成功”，下方按真实排队/运行/失败/中断/成功显示。
4. 展开“事实对照（只读快照）”：显示原问题意见、操作者/原因、父子任务状态/模型/输入摘要、
   登记编号、四类像素计数及 `delta`、NoData 分母与占比。`same_total_pixels` 只是数量相同；
   `comparable_pixel_space` 只在相同输入字节时为真，不同输入未核实配准；不报精度或平方米。
   子任务未成功、证据不齐时对照数字为 `null`，明确“待完成/记录缺失”，不填 0。
5. 若整页重载丢失原上传表单：面板列出 **prepared** 记录，可点**“确认原提交（同号）”**
   （`POST /corrections/<id>/resume`），保持原请求号，不重传文件、不新建版本。该显式动作的语义：
   **已存在子作业时只补关联、不重新推理**；**不存在子任务时，该显式动作可按保存的同模型快照首次
   提交**。普通 GET、启动恢复与刷新始终不提交。若回执未知（离线/超时/协议/坏JSON/5xx），先确认原
   意图（同号）再考虑明确新建版本，不要直接换号。
6. 查看子作业时（含失败/中断），面板只读显示“本作业由整改产生”的来源记录与对照，
   不显示旧成功图。可下载“整改对照 JSON（UTF-8）”，含完整 snapshot/比较与无真值边界。

边界：人工意见不是真值；整改不证明自动修复或精度提升，也不代表原 TIFF 通过 P0 质检；
原输入/模型/掩膜/意见/治理快照一律不改；同一 root 最多 50 条修订，本地面板只展示事实。

## 客户端深层事实交叉校验（DEV-20261015-017）

`RecognitionClient` 不再只校验 JSON 类型，而是按真实 `GET /corrections/<id>` 契约重算并逐项交叉比对；
任何不一致都抛 `ApiError(protocol)` 并停止下载/展示（不填 0 冒充、不降级呈现）：

- 快照父事实与父摘要的输入/模型/来源场景文件/许可/样本类别逐项一致；问题意见必须是
  `questioned`/`rejected`，且父 job / review_id / input / model / run_seq 与父作业一致；
  `parent_registration` 与父作业 `governance` 一致。
- 快照内部一致性：`changes` 与整改记录一致；修订元数据 = 父事实叠加 `changes`；
  `changed_fields` 为实际差异、`bytes_changed` 为摘要是否实际变化；未替换字节不得改动输入。
- 修订事实与子摘要一致（输入/文件/全部元数据），且子作业模型须与父作业相同。
- `evidence_complete` 由客户端按事实重算（成功运行 + 四类非负整数正合计 + 固定 5 产物唯一）；
  与声明不符即拒绝；证据不齐时 NoData 与像素对照必须为 `null`，不得补零。
- 对照复制字段与快照逐项一致；`input_sha256`/`model_sha256` 父子映射及 `same_*` 按事实计算；
  像素父子四类与各自摘要相同、`total`=四类和、`delta`=child-parent、`same_total_pixels` 与
  `comparable_pixel_space`（仅相同输入摘要才为真）按事实计算；子最新意见必须属于该子及其运行。
- NoData 取 255 类像素、分母为四类合计、`ratio=round(pixels/denominator,6)`，须为有限数值且
  `bool` 不计为数值。
- 记录：`prepared` 不得带子作业、`linked` 必须带子作业、根≤父<子单向；父为 `synthetic_test`
  时 `is_synthetic_case` 不得为假（沿链继承为真允许）。
- `changes` 白名单/类型本地先校验，仅空白可选字段规范化为 `None`（与已修 015 后端一致）。

独立复核入口（只读，均由真实服务生成合成 fixture）：`tests/corrections/test_client_integrity.py`；
行为夹具：`tests/corrections/test_correction_client.py`。

## 面板提交状态与治理前置（DEV-20261015-018）

本轮只改 `agrolake_web/corrections_panel.py`（提交状态机、治理前置、NoData 展示），不改后端/
模型/客户端契约。真实行为如下：

- **每个作业只保留一个“当前意图”**：当前内容相同重复点击复用同一请求号（服务端幂等复用同一
  子作业）；一旦内容变化（含 A→B→A）一律生成新请求号/新版本。不再使用历史 hash→UUID 表。
- **回执未知必须锁新意图**：`offline`/`timeout`/`protocol`/`badjson` 以及 HTTP 5xx（含 503，
  可能已 `prepared`）都视为“结果未知”，保留原请求号与原 payload（每作业仅一份），并禁用
  “创建整改并复跑”，只允许“确认原提交（同号）”。确认时先按只读列表找原记录：`linked` 仅确认、
  `prepared` 调 `resume`；列表里没有才用原 payload 同号重试。确认成功后释放原 payload。
- **同父存在 `prepared` 时禁新建**：整页重载丢失表单后仍据此禁用创建入口，prepared 记录在
  “待确认的整改”里点“确认原提交（同号）”（`POST /corrections/<id>/resume`），不重传文件、
  不新建版本、不重排队。已 `failed`/`interrupted` 的子作业不重放。
- **治理前置**：创建入口要求父作业已登记治理血缘（`GET /jobs/<id>/lineage` 的 `registered`）。
  未登记（或无法确认）时隐藏创建表单并给出“先登记输入资料”的下一步；历史整改与来源仍可查看。
- **超限替换文件禁整条提交**：替换 TIFF 超过 40 MiB 时明确报错并阻止提交，不会忽略替换文件
  却只提交元数据。
- **NoData 实际分母与占比**：对照区显示父/子 `255 类像素 / 四类合计分母（占比）`
  （如 `2 / 12（16.67%）`）；子任务未成功或证据缺失时显示“待完成/缺失”，不以 0 冒充。
  父作业“未复核”不再误显示成“子任务未复核”。占比只是事实计数，不是准确率。
- **子任务导航**：提供“查看子任务 #<id>”按钮，通过安全回调只设置 `rec_selected_job` 并重跑，
  不直接改动已创建的 `rec_history` 控件；无自动提交、无自动推理。

## 客户端坏响应边界与面板意图/提示（DEV-20261015-020）

本轮只做加法与边界收尾，不改 018 已通过机制：

- **必需字段存在性**：客户端对整改详情/任务摘要要求已知必需字段存在，键缺失抛
  `ApiError(protocol)`，与**显式 `null` 合法值**区分；缺 `snapshot.revised.source_link`、
  缺 `child.latest_task_review` 不再泄漏原生 `KeyError`。
- **整改 SHA 只接受字符串**：所有新增整改 SHA 摘要先 `isinstance(x, str)` 再匹配十六进制，
  不做 `str()` 强转；把 64 位十进制整数当摘要会被拒绝。
